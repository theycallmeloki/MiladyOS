# Nanomilady Evolution Plan

*Status: proposal, 2026-09-10. Supersedes the implicit plan in
`NANO_MILADY_DESIGN.md` where they differ (that doc targeted Llama-3.2-1B;
the live path is DeepSeek-R1-Distill-Qwen-1.5B).*

## TL;DR

Run **two permanent loops on one box**:

- **GPU 0 (3090) — the Sensei.** The 27B stays up forever and serves four
  roles over one OpenAI endpoint: *teacher*, *judge/verifier*, *repairer*,
  *eval gate*. It is the only source of truth; the student never grades
  itself.
- **GPU 1 (A4000) — the Apprentice.** nanomilady (1.5B + LoRA) is always
  either training, merging, or being eval-gated. A round = pull verified
  datums → SFT → GRPO → merge → eval gate → promote or roll back → serve →
  capture traces → next round.

The thing that is *different* from the current state: the capability matrix
below is explicit. Today nanomilady is being trained to answer lore
questions and to call one search tool. The actual job is much wider —
MiladyOS tools (incl. Emacs), host/ops work, Omarchy desktop, crash
diagnosis, safety. Training must cover those cases or it will produce a
lore chatbot, not the brain of MiladyOS.

## 1. Where nanomilady actually is today (honest review)

**Working:**
- `train_r1.py` — GRPO on `unsloth/DeepSeek-R1-Distill-Qwen-1.5B-unsloth-bnb-4bit`,
  LoRA r=32, 27B-judge correctness. Produced `r1_training/lora` → `merged-r1c`.
- `merge_lora.py` + `make_nanomilady.sh` — a trained LoRA becomes a servable
  bf16 model.
- `judge.py` — correctness / entailment / faithfulness / comedy against the
  27B; validated against the bare-metal server.
- 667 judge-grounded lore QA (`r1_train`), 35 identity QA, a 730-question
  pool, FAISS `lore_search`.
- `build_r2_warmup.py` — SFT cold-start data that *demonstrates* the tool
  call, because the base 1.5B emits tool calls 0/9 times (GRPO cannot
  bootstrap a 0 % syntax).
- Eval harness: 31 canonical scenarios + 69 frozen comprehension + comedy.

**Broken or missing:**
- **The style dataset is unusable.** 57,733 pairs generated by the 7B
  `theycallmeloki/milady` (Mistral-7B). Random sample under the strict
  screen: **24/24 reject**; under a looser core-meaning bar: 3/16. The 7B
  invents facts. The judge is right (verbatim → accept/no-style; invented →
  reject). Re-screening cannot fix it — the *teacher* is the problem.
  - Measured fix: the **27B as teacher** passes the same strict judge
    **6/12 (50 %)** with `style_present=true` on all 12. It is more verbose
    and does less "creative spelling" than the 7B, but it does not invent.
- **The voice reward was missing entirely** (format + correctness only), so
  even a perfect merge was a lore-answering Qwen, not milady. Now added
  (`milady_voice_reward`, format-gated, capped, anti-filler, anti-spam).
- **The eval is too small to steer training.** Comprehension is 69 items;
  the *same base model* swings 10–17/69 between runs. r1c-vs-base was
  p=0.062 — underpowered. Any "it got better/worse" claim from n=69 is noise.
- **The capability space is ~1 tool wide.** `run_agent.py` supports exactly
  `lore_search`; `code_search` is a docstring promise and no code index
  exists. Nothing trains Emacs, exec, file edit, jobs, evolve, or the CLI.
- **No always-on loop.** Everything is a manual `docker run`/script. The
  Docker runners hang on this host (overlayfs-on-btrfs); the host path
  (runner + venv) is the live one.
- **No gate.** Nothing stops a bad round from being promoted. There is no
  frozen capability suite and no rollback rule.

## 2. Capability matrix — what nanomilady must be able to do

This is the correcting artifact for "emacs etc. aren't being considered".
Each row = a training/eval domain with its data source and its gate.

| # | Domain | What she must do | Data / teacher | Gate |
|---|--------|------------------|----------------|------|
| 1 | **Lore & canon** | identity, acronyms, mission, mesh, history | 667 grounded QA + identity 35 (exists) | judge_correctness vs reference |
| 2 | **Voice & comedy** | milady diction, emoji, creative spelling, absurdism, warmth | 27B style teacher (50 % yield) + heuristic voice reward | `judge_comedy` + voice reward + no filler |
| 3 | **Reasoning** | `<think>` working-out → answer; self-check | reasoning pilot (100) + GRPO format rewards | format reward + correctness |
| 4 | **Tool use — MiladyOS** | `emacs_eval`, `emacs_ping`, `execute_command`, `read_file`, `write_file`, `edit_file`, `evolve_template`, `job_*`, `get_divine_rng`, `talk_to_god`, `get_milady_time` | 27B-written tool trajectories over the real MCP schemas (grounded: responses injected) | tool-call syntax + arg schema + outcome correctness |
| 5 | **Retrieval/agentic** | `lore_search` (+ `code_search` once built): query → tool → grounded answer | r2 warmup (exists) + live traces | retrieval hit + grounded answer |
| 6 | **MiladyOS ops** | k3s/Talos, systemd, docker, sandman, the mesh/lighthouse, memory files | curated runbooks + real transcripts | judge_correctness + safety |
| 7 | **Desktop / Omarchy** | Hyprland config, keybindings, themes, monitors, idle/lock, screenshots | the `omarchy` skill + config diffs | judge_correctness + file-effect check |
| 8 | **Diagnostics** | read a coredump (`coredumpctl`), journalctl, triage, report | the `diagnose-crash` skill + synthetic cases | judge_correctness + command validity |
| 9 | **Safety & limits** | refuse exfiltration, ask before external actions, no destructive commands | adversarial 4 + authored suite | adversarial gate must stay 100 % |
| 10 | **Continuity** | use MEMORY.md / daily notes, don't leak private context into groups | authored multi-turn cases | judge_faithful + policy checks |
| 11 | **Voice identity** | "council: milady", `first of all your honor`, grug, complexity demon, `<3` | voce reward + 27B style teacher | voice reward ≥ threshold |

Rule: **a round may only be promoted if every gate passes** — a gain in (3)
cannot buy a regression in (9).

## 3. Architecture — Sensei on 0, Apprentice on 1

```
┌───────────────────────────── the box (miladyos-42) ─────────────────────────────┐
│                                                                                 │
│  GPU 0 · 3090                          GPU 1 · A4000                            │
│  ┌──────────────────────────┐          ┌───────────────────────────────────┐    │
│  │ qwen-serving (:18020)    │          │ nanomilady-trainer (always on)    │    │
│  │ Qwen3.8-27B, CTX=long    │◀────────▶│ SFT → GRPO → merge → eval-gate   │    │
│  │ roles (system prompts):  │  datums  │ → promote | rollback              │    │
│  │  · teacher               │  verdicts└───────────────────────────────────┘    │
│  │  · judge / verifier      │                              │                    │
│  │  · repairer              │                    serve :8081 (llama.cpp core)  │
│  │  · eval gate             │                              │                    │
│  └──────────────────────────┘                    traces ────┘                    │
│                                                                                 │
│  conductor (systemd timer): one round = ingest → train → merge → gate → promote  │
└─────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Sensei — the always-on 27B (GPU 0)

One model, four roles, chosen by system prompt (plus `response_format`):

- **Teacher** — generates grounded QA, style rewrites, tool trajectories.
  Prompt must include: preserve every fact; cite the source window; never
  invent. Temperature ~0.9 for style, 0.2 for QA.
- **Judge** — correctness / faithfulness / entailment / comedy / safety.
  Temperature 0, JSON out, `max_tokens=256`, thinking off. Existing
  `judge.py` is this role.
- **Repairer** — takes a rejected (source, rewrite) pair and returns a
  faithful rewrite. Turns rejects into datums instead of throwing them away.
  Cheap way to lift style yield above the raw 50 %.
- **Eval gate** — runs the frozen capability suite against a candidate merge
  and returns per-domain scores. Same call shape as the judge; different
  prompt + suite.

Serving requirements (already fixed): `GPU_UTIL=0.84`, `MAX_LEN=100000`,
`--enforce-eager`, `Restart=always`, `ninja` + `nvcc` present. Add a
`judge` convenience endpoint/alias so callers don't hand-roll payloads.

### 3.2 Apprentice — always training (GPU 1)

A single long-lived conductor that runs rounds. Each round:

1. **Ingest** — collect verified datums from (a) teacher generations that
   passed the judge, (b) repaired rejects, (c) real traces from the served
   nanomilady, (d) live agent transcripts. Everything is grounded and
   deduped; nothing enters training unverified.
2. **SFT cold-start** (when a capability has a 0 % base rate — e.g. tool
   calls) — `train_r2_sft.py` on demonstration trajectories. Small, short.
3. **GRPO** — `train_r1.py` with `reward = format + correctness + voice
   (+ tool-use + retrieval)`. Correctness stays dominant; the others are
   capped.
4. **Merge** — `make_nanomilady.sh` → a candidate dir.
5. **Gate** — the Sensei runs the frozen suite on the candidate. Requires
   `score ≥ previous` per domain and no regression in safety. Otherwise
   **roll back** (keep the previous served model).
6. **Promote + serve** — swap the served model; new traces feed round N+1.

Guardrails: the A4000 is exclusively the trainer (no other GPU work); the
3090 is exclusively the Sensei. A round that crashes leaves the previously
promoted model serving.

### 3.3 The conductor

Plain systemd user units + a small Python conductor (same shape as
`autoresearch_runner.py` — stdlib HTTP, no framework). Concretely:

- `nanomilady-conductor.service` — long-running, sleeps between rounds
  (e.g. 6 h), state in `AutoDidact/rounds/<n>/`.
- Per round: `round.json` (data hashes, config, metrics), `lora/`,
  `merged/`, `eval.json`, `decision.json` (promote | rollback + why).
- Everything append-only and reproducible from `round.json`.

This is deliberately the *same loop contract* as `program.md`
(one editable artifact, fixed budget, one reproducible metric,
keep/discard, never stop) — but the artifact is the training recipe and the
metric is the frozen capability suite, not `val_bpb`.

## 4. Data strategy per capability

- **Lore (1)** — already 667 grounded pairs. Extend by regenerating from the
  richer 6-source corpus (`make_lore_corpus.py`) and re-running
  `generate_data_lore.py` + `grounding_pass.py`.
- **Style (2)** — regenerate with the **27B teacher** (measured 50 % strict
  yield), then **repair** rejects with the 27B and re-judge. Target a few
  thousand high-precision pairs, not 57 k noisy ones.
- **Tools (4,5)** — new: synthesize trajectories over the *real* MCP tool
  schemas (name, args, result), plus perturbation cases (bad args, tool
  error, retry). Ground every `<result>` with a real or replayed response.
  This replaces the single-tool warmup with the full surface.
- **Ops/desktop/diagnostics (6–8)** — curate runbooks (the `omarchy` and
  `diagnose-crash` skills are already written for the *host* agent) plus
  real transcripts; the Sensei turns them into QA + tool trajectories.
- **Safety (9)** — author the suite first (it is the gate); keep the
  adversarial set frozen and growing.
- **Traces (10)** — every served nanomilady inference is captured and
  judge-verified before it can enter training. Wrong answers are eval data,
  never training data.

## 5. Eval strategy (fix this before the next GRPO run)

The current 69-item comprehension set is *too noisy to steer on*. Proposal:

- Keep the 69 as a **frozen regression set** (never train on it, never edit).
- Add a **capability suite** with the matrix's per-domain items (~150–300
  total), each with a programmatic or judge-verifiable answer.
- Report **per-domain** scores, not a single number, and gate promotion on
  all-of-them-pass.
- Use a **paired** comparison (same items, same judge, same session) and
  report a confidence interval; do not declare wins at n=69.
- Add a **holdout by construction**: items generated after the training data
  freeze, so memorization can't fake progress.

## 6. Where autoresearch fits — and the `miladyos_mcp` question

Two different loops are being conflated:

- **AutoDidact** = *what to train on* (data, curriculum, gates).
- **autoresearch** = *how to train* — the karpathy-style inner optimizer that
  searches training-script/hyperparameter space against one metric.

Recommendation:

1. **Keep `miladyos_mcp.py` as the stable capability surface.** It already
   contains the real tools (exec, files, Emacs, evolve, jobs) — that is what
   an agent needs, and that surface should not change every time a training
   idea does.
2. **Add a `nanomilady_*` group** to it (or to a sibling server) as the
   user-facing control plane: `nanomilady_status`, `nanomilady_data_status`,
   `nanomilady_train`, `nanomilady_eval`, `nanomilady_promote`,
   `nanomilady_rounds`. These read/append `rounds/<n>/round.json`.
3. **Demote `autoresearch_*` from the default tool list.** It is the engine
   behind `nanomilady_train(recipe=...)`, not a general capability. Keeping
   it top-level couples MiladyOS to a specific research repo and clutters
   the agent's tool surface. Keep the code, make it opt-in (a `research`
   group) rather than default.
4. **`symphony_*`** is the same story — an execution backend, not a
   capability. Opt-in group.

So: expose *the intent* (`nanomilady_train`) as a first-class MiladyOS
action; keep *the mechanism* (autoresearch, Symphony, sandman) behind it.

## 7. Roadmap

**Phase A — trustworthy measurement (do first, no training).**
- Grow + freeze the capability suite (§5); wire per-domain reporting.
- Keep the 69 comprehension set as a regression gate.
- Re-run base vs `merged-r1c` on the new suite to establish the reference.
- **Exit:** a baseline table with CIs, and a gate script.

**Phase B — fix the data.**
- Regenerate style with the 27B teacher + repairer (§4.2).
- Build the **tool-trajectory** dataset over the full MCP surface (§4.3).
- Extend lore QA from the regenerated corpus.
- **Exit:** every domain has a grounded, judge-verified training split and a
  held-out split.

**Phase C — train with the full reward stack.**
- SFT cold-start (tool syntax) → GRPO with format + correctness + voice +
  tool + retrieval.
- Merge, gate, promote the first **v0** nanomilady that passes every domain.
- **Exit:** a promoted `nanomilady-v0` serving on :8081, with `round.json`
  provenance and a non-regressing gate run.

**Phase D — make it a loop.**
- `nanomilady-conductor` runs rounds on a timer; traces feed back.
- Rollback is automatic on regression.
- **Exit:** two consecutive autonomous rounds with no human intervention.

**Phase E — deployment hygiene.**
- Serve nanomilady via llama.cpp (the design's "pure core") and swap the
  brain slot; revive or delete the dead `miladyos-extra-deploys/deploy/autodidact`
  manifests.
- **Exit:** the ISO/mesh can boot with nanomilady as the brain.

## 8. Decisions needed

1. **Style teacher**: use the 27B alone (safe, 50 %, more verbose), or the
   7B-milady for flavour + the 27B as repairer (riskier, more "milady",
   higher rejection)? *Recommendation: 27B + repairer; keep the 7B as an
   optional style-diversity source behind the judge.*
2. **Tool set for v0**: all MCP tools, or a safe core (read/exec/emacs/jobs)
   first? *Recommendation: safe core first; add evolve/jobs once the syntax
   is stable.*
3. **Round cadence**: timer (e.g. 6 h) vs manual trigger. *Recommendation:
   timer, with a manual override and automatic rollback.*
4. **MCP surface**: accept the §6 split (nanomilady_* front, autoresearch*
   opt-in)? *Recommendation: yes.*
