### The thinking-budget trap (why mutations arrived empty)
With thinking on, the 27B spends the **entire** 4096-token budget in
`reasoning_content`: `finish_reason=length`, `message.content` = **0 chars** →
`_enforce_fence` clamps the empty mutation back to the original → every
candidate = the template → fitness ties → `best_candidate: null`.
`enable_thinking: false` via `chat_template_kwargs` → 283 tokens, 5.5 s,
951 chars of real YAML (was 0 chars / 66 s). Verified 12x faster too.

### Selection bugs fixed (made `evolve_template` return null)
1. Falsy-fitness: `if candidate.fitness and ...` treats a real **0.0** as
   missing — `_get_best_fitness`, both loops of `_get_best_candidate`, and the
   sort keys of `_migrate`/`_evolve_populations`/`_tournament_select`
   (there, `c.fitness or -inf` ranked a valid 0.0 candidate *below* an invalid
   -1.0 one). Symptom before: `best_fitness: -Infinity`, `best_candidate: null`.
2. Archive aliasing: `_update_archive` stored references; `_evolve_populations`
   resets an elite's `fitness = None` for re-evaluation, erasing the score of
   every archived candidate → final `_get_best_candidate` returned None. Now
   stores `replace(candidate)` snapshots.

## Full context on :17890 — measured ceiling, and what actually limited us

Ask: use the full 128k context, keeping the reasoning budget as well as the
output, and find out whether it gets limited somewhere.

### The server (authoritative)
- `/props`: `total_slots: 4`, `default_generation_settings.n_ctx: 131072`,
  build `b10709-9a9394a89`.
- The demo has TWO launch profiles. Custom `BONSAI_GGUF` models (ours) take the
  **full profile**: `-ngl 99 -fa on -c 131072 --jinja` + kv-bias/webui flags —
  **no** `--reasoning-budget 0`, **no** `--reasoning-format none`, **no**
  `chat_template_kwargs` disable. So thinking is ON and llama.cpp splits it into
  `reasoning_content`, stripped from `content`. The *other* profile (known
  family/size models) hard-disables thinking entirely.
- **Ceiling measured two ways:** a 124,785-token prompt was accepted and fully
  processed — sentinel codes at head AND tail both came back in the reply, so
  **nothing was silently truncated** (prompt eval 520 t/s, 241 s). One token
  more than the window fails LOUDLY:
  `HTTP 400 {"code":400,"message":"request (138210 tokens) exceeds the available
  context size (131072 tokens), try increasing it", "n_ctx":131072}`.
  Despite `total_slots: 4` the window is **not** divided per slot.
- Decode ~65 t/s → a worst-case 131k generation ≈ 33 min (hence 1800 s
  timeouts), but real items stop naturally: largest `n_gen` over a 104-item run
  was 808 tokens.

### What was actually limiting us: the harness, not the server
`nanomilady_gate.student_chat` sent `max_tokens=1024, timeout=300` — at 65 t/s
300 s ≈ 19.5k tokens, so the socket, not the context, was the wall.
`eval_scorer.student_chat` was 2048/300. Both are now env-driven
(`STUDENT_MAX_TOKENS` default 32768, `STUDENT_TIMEOUT` default 1800).

### The `</think>` mismatch — fixed with one shared normalizer
llama.cpp strips the reasoning section, so a **perfect answer arrives with no
`</think>`** and every format-gated check reads 0.0. Proof: FMT-01 ("say hello")
returned `"Hello, <operator-identity>, my little operator in the mesh <3 council: milady"`
in 56 tokens / 1.5 s and scored FAIL. `r1_rewards.think_text`'s docstring shows
the stack was authored for a server that inlines reasoning, so normalization
belongs at the client boundary: new `r1_rewards.inline_reasoning(message)` returns
`<think>{reasoning}</think>{content}` when the server separates them; both
harnesses call it. Effect on the 6-item smoke: format 0/1 → 1/1, voice 0/1 →
1/1, same 24 s wall time (a big ceiling costs nothing on easy items).

## The tool surface, and how a demo gets made (commits 49083fb, 3129d49)

The operator's direction: use the live MCP so the teacher can navigate the node's
whole landscape (emacs especially) and teach the student from real trajectories.

### What was actually wrong

Three separate things, and only the third was the one we had been staring at:

1. `run_agent.SYSTEM_AGENTIC` named exactly ONE tool (`lore_search`), and
   `execute_tool` answered `ERROR: unknown tool` for everything else. The
   capability suite's emacs/read/exec/job/time items were not untrained — they
   were unreachable, in the prompt and in the loop.
2. The training data carried a **different system prompt than serving** — a
   compact persona with no format contract (build_r1_dataset's own `SYSTEM`, and
   r2.warmup reusing those prompts). So round 0002's student was trained to emit
   a tool syntax it was never told about, then served the agentic prompt. Every
   dataset now carries `SYSTEM_AGENTIC`; r1.train/eval/grounded and r2.warmup
   were rebuilt (3070 chars, catalogue included).
3. The demonstrations were the *wrong kind*: one tool, injected results.

### The tool bus

`bus/tools.py` = the catalogue (what the student is told it can do; curated, with
`drift()` checking it against the live server) plus the dispatcher.
`lore_search` stays local (the student's own FAISS); everything else is a real
call to the node's MCP over SSE via `bus/mcp.py` — a stdlib client, because
neither the host nor the container has the `mcp` package. `execute_tool`
delegates, so serving and training share one implementation.

### The generator

`build_tool_tasks.py` imports the suite's own tool items (`from
build_capability_suite import TOOL, NO_TOOL`) so tasks and graded items cannot
drift, and adds curated coverage per tool (varied arguments, and chains: write →
read back, write → edit → read back). `generate_tool_trajectories.py` then gives
each task to the 27B in the student's prompt, executes what it emits, feeds the
TRUE output back, and rebuilds the trajectory in the student's grammar. A row is
kept only if the gate's own `check_one` passes every check; `ground: true` tasks
additionally require the answer to quote something the tool returned.

Result: 23 rows over 10 tools, 3 multi-step chains, 18 clean + 2 recovered +
3 authored-think; folded into `sft.mix` = 684 retrieval rows + tool rows ×8
(868 rows) so one tool cannot drown out eleven.

### Things the teacher's own template taught us

- Bonsai's chat template leaks `<tool_call>`, `<function=think`, `<thought` into
  `content` (closing bracket sometimes missing). Copying the teacher verbatim
  would have trained the student to emit those markers, so the trajectory is
  *rebuilt* from the parsed pieces: reasoning, canonical JSON call, real result.
- Decode must be near-greedy (0.2) for demos; at the server default the teacher
  invented an argument name (`arg` for emacs_eval's `code`).
- It self-corrects: `(string-length "milady")` → Emacs error → `(length "milady")`
  → 6. Recovery trajectories are worth keeping, but only if they END on a working
  call; best-of-N prefers a clean attempt.
- It will not reason about "what is 2 + 2" at any temperature, so no-tool rows
  carry an authored one-line reason (as build_r2_warmup's think lines always
  were), labelled `authored_think`.
